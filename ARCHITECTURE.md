# Architecture

## Boundaries

| Layer | Location | Responsibility |
|---|---|---|
| Desktop shell | `apps/desktop/src` (React) | Views, editors, stores (zustand). No direct file or network access. The world editor's 3D view uses three.js, loaded only when it is opened. |
| Native backend | `apps/desktop/src-tauri` (Rust) | Projects, SQLite, Git snapshots, engine discovery, process runs, Godot installer, AI provider HTTP, the `gsplay:` scheme that serves web builds to Play here (`play.rs`), the games' saves that Play here keeps (`play_saves.rs`), pointer capture for Play here's mouse look (`pointer_lock.rs`), and native input and window pictures for the self-test only (`native.rs`). |
| Rules core | `packages/rules-core` | Graph schema, node registry, validator, compiler to IR v1, interpreter, conformance fixtures. |
| Domains | `packages/oware`, `packages/explore` | Node libraries, hosts, reference engine (Oware), world schema (explore). |
| Foundations | `packages/rpg`, `packages/learn`, `packages/plugins` | Creature catalog and encounters, lessons and quizzes, plugin manifests. |
| Projects | `packages/project` | Manifest schema, safe paths, templates, engine data sync. |
| Agents | `packages/agents` | Typed operations, apply/validate/diff, skills, agents, router, two-attempt run loop. |
| Engine runtimes | `engine-addons/godot/gamestudio_runtime`, `engine-addons/unity/GameStudioRules`, `engine-addons/unreal/StudioRules` | The rules VM in GDScript, C# and C++ (plain C++17 without exceptions or RTTI, so it builds inside an Unreal module), each mirroring the TypeScript interpreter and shipped into every project of its engine. |
| Templates | `templates/` | Godot exploration, XR additions, Unity exploration (C# world builder, player, self-test, batch build script), Unreal exploration (C++ module: level builder, character, HUD, self-test), C++/SFML project files (bundled with `import.meta.glob`). |

## Key decisions

1. **Godot is the source of truth for scenes.** The studio edits engine-neutral data (`data/world.json`, rule graphs) and syncs compiled data into `godot/gamestudio_data/` on save. Rules sync only when every graph compiles. The world editor's 3D view is a preview of that same data, not a second scene: `views/world/level3d.ts` builds each object from the shapes, sizes and colours in the Godot template's `world_builder.gd`, with the same rotation direction, sun direction and exponential fog formula, and edits made in 3D go through the same document, validation and undo history as the map. Clicks hit simple stand-in shapes (cylinders, boxes, discs) rather than the meshes, which keeps picking cheap and lets the tests run without a GPU.
2. **Rules are deterministic data.** Graphs compile to a structured IR interpreted identically by TypeScript, GDScript, C# and C++. Shared fixtures enforce identical results: the 22 steps pass in Godot 4.7.2, and `runtimes.test.ts` builds the C# runtime as C# 9 (what Unity 6 compiles) and the C++ runtime with Unreal-like flags (no exceptions or RTTI, warnings as errors) and runs the same steps. Number-to-text formatting is spelled out with integer steps in every runtime, and the C# and C++ versions round `x * 100 + 0.5` in two steps so a fused multiply-add cannot change a printed digit. Each engine's game answers the same host calls as the studio's simulator (`ExploreSimHost`).
3. **Oware variant settings live on nodes.** The Abapa graph is checked move-by-move against an independent reference engine for 8 settings combinations.
4. **Security by construction.** File commands need a registered project root; symlinks and dotfiles (except `.gitignore`/`.gitattributes`) are refused; imports accept only user-picked or dropped paths; Git runs with hooks and signing disabled; child processes lose credential variables; installer downloads are HTTPS-only, redirect-restricted, SHA-512 and code-signature checked; AI keys come only from the environment and are bound to fixed endpoints; cloud calls need explicit opt-in.
5. **AI proposes, people decide.** Models return typed operations (JSON schema in the strictest provider subset, with property order preserved end to end because constrained decoding follows it). Proposals apply to copies, are validated and diffed, and are written only after approval with snapshots before and after.
6. **Unity and Unreal are driven through their own command-line tools.** The studio never installs either. Unity projects pin the installed editor in `ProjectSettings/ProjectVersion.txt` (without it Unity rewrites the package list and downloads its defaults) and use built-in modules only. `StudioBuild.cs` creates the scene and a lit material at build time, because a level built at runtime leaves nothing that keeps the Standard shader in the build. Unreal projects are a small C++ module (UnrealBuildTool compiles it, BuildCookRun packages it) that builds the level at runtime on the engine's empty Entry map; they cook SM5 shaders only (Unreal 5.8 falls back to SM5 on M1 Macs), package with `-package` (otherwise the .app has no content), start with `-LLM` (otherwise Unreal 5.8 can crash on a first launch, in a race inside its memory tracker), and run in Apple's App Sandbox, so the game writes only inside its own container. Unreal counts as installed only once `UnrealEditor.app` exists, and builds wait until Xcode is selected and its Metal toolchain is installed. Both games load the compiled rules from their data folder and fire the same events as the Godot game (start, collect, enterZone each time the player walks in, interact on E), and print the same GSTUDIO rule lines for the run console when started with the telemetry flag.
7. **Builds go to `exports/`, outside the engine folders and ignored by Git.** Godot exports use the project's `export_presets.cfg`; for older projects the studio lists the changes it needs (preset, ETC2/ASTC import, ignore rule) and writes them only after the user agrees. Export paths must stay inside the project. App bundles run through the executable named in their `Info.plist`, and every export or build is followed by the built game's own headless self-test. Windows and Linux builds are 64-bit x86 programs with the game's data in a `.pck` beside them (`planGodotDesktopExport`, `ExportTarget` in `lib.rs`). They cannot run on a Mac, so their run ends with Godot here running the exported pack (`--main-pack`, or the program itself when a preset embeds the pack) through the same self-test. That covers the game data, not the program. The engine test runs the programs too when `CONTAINER_BIN` is set, in x86-64 Debian containers with no network and the build mounted read-only (the `.exe` under Wine from Debian's packages, `tests/containers/wine`).
8. **Play here runs the web build in a sandboxed frame.** The Play view exports the Godot project with its Web preset (the single-threaded template, so no cross-origin isolation or SharedArrayBuffer is needed) and shows Game Studio's own page for it (`src-tauri/assets/play-shell.html`) in an iframe with `sandbox="allow-scripts allow-pointer-lock"`. The frame's origin is opaque, so it cannot read the studio page or its storage; Tauri injects its scripts and invoke key into the main frame only, so the frame's command calls are refused; and the `gsplay:` scheme serves only plain files of builds opened in this session, each under a random token, with no network port. The page starts the engine with `--studio-telemetry` and posts its output to the Play view, which feeds it into the same run records as a Godot window. The CSP allows frames from `gsplay:` and nothing else.
   The frame has no storage, so the page stands in for the browser database Godot keeps `user://` in (`assets/play-saves.js`, only the calls Emscripten's IDBFS makes) and posts each save to the Play view, which checks it (`views/play/saves.ts`: plain files and folders under `/userfs/`, at most 4,096 entries and 32 MB) and keeps it on disk in the studio's data folder, one file per project (`play_saves.rs` checks again); the game gets its saves back before it starts. Mouse look works because `pointer_lock.rs` answers WebKit's pointer-lock question, which wry's web view delegate leaves unanswered (WebKit then refuses every request); WebKit still requires a click, a frame allowed to lock the pointer and a focused, visible window, and Esc gives the pointer back.
9. **Web builds draw the sun's shadows themselves.** Godot 4.7's Compatibility renderer, the only one a web build has, draws a shadow-casting light in a second pass and adds it after converting each pass for the screen, which washes out everything the sun lights (measured on the template level: ground `#a3f6ac` where Forward+ draws `#7ba678`; the same in Godot's desktop Compatibility renderer, so it is not the browser). Godot's `scene.glsl` calls `linear_to_srgb` on that pass in every mode: turning on glow or adjustments (which move tonemapping into a later pass) still left lit ground almost twice as bright, so no setting fixes it. With the sun's shadows off, the sun is drawn in the same pass as the sky light and the colours match Forward+ within a few units. The templates therefore turn them off on that renderer and draw shadows from the sun's point of view: a SubViewport with an orthographic camera along the sunlight renders the level (unshaded, transparent background) so its alpha is the outline of everything that casts a shadow, and the ground's material reads that outline in its `light()` function and drops the sun's light beneath it, keeping the sky's (`sun_shadows.gd`, `shaders/ground.gdshader`). Shadows land only on the ground, grass and pitch, not on other objects; their shapes, places and colours match the desktop renderer's (2026-11-21, pictures in `docs/evidence/graphics-*`). This replaced the earlier soft ovals of shade.
10. **Imported models are plain glTF files placed by the layout, not baked into scenes.** A world object of type `model` names a `.glb` or `.gltf` under the engine project's `assets/` folder (the schema refuses anything else, including `..`). Godot loads it with `load("res://assets/...")`, so it must have been imported: a run adds Godot's import step whenever a file under `assets/` is newer than its `.import` file (`builds::godot_needs_import`). The game puts a box around the model's meshes for collision; the studio's 3D view draws the same file with three.js's GLTFLoader through the asset protocol (only the project's asset folders are in its scope) and uses the model's measured size as its click shape. A `.gltf` refers to its buffers and textures by relative path, which file URLs cannot resolve, so the view maps each reference back into the model's folder (`siblingAsset`) and refuses any that would leave `assets/`. Only Godot projects place models; Unity and Unreal import models in their own editors.
11. **The free library is Poly Haven, fetched by the backend.** Poly Haven's API needs no key and its assets are CC0. The Rust side talks only to `api.polyhaven.com`, `dl.polyhaven.org` and `cdn.polyhaven.com` over HTTPS, checks every file against the size and MD5 the API lists before writing anything, writes only inside the project under checked names, and returns previews as `data:` URLs so the page's CSP stays closed to the internet. Downloads are recorded in the asset index with licence CC0 1.0, the authors and the source page.
12. **A game idea becomes a project through the same validated operations as the chat.** The Producer (one model call) picks one of five templates and writes a brief, including what the template cannot do; the template's specialist (level designer, world builder or rules engineer) then changes the template's starting content with typed operations that are applied to copies and validated, with warnings such as coins out of jump reach (`reachWarnings`). The user sees the plan and the changes; on Create the project is made from the template, the same operations are applied to its real documents, and snapshots bracket the change. A linked page is fetched by the backend (http(s) only; names resolving to loopback, private, link-local or similar addresses are refused, again after each redirect; at most 2 MB, text only) and given to the model as data, with instructions to keep only genre and mechanics of an existing game.
13. **Characters are imported glTF files animated by name, not rigs built in the studio.** The player's `character`, a villager's `model` and a placed model's `animation` name files and animation clips; the game (`models.gd`) and the 3D view (`level3d.ts`) fit a character to its height by its bounding box, turn the player's by `turn` (glTF characters face +Z, the player -Z) and pick clips by name, comparing names without case or punctuation because importers rename them, and guessing idle, walk, run and jump from the names when none is chosen (`guessClips`). The 3D view clones characters with three.js's SkeletonUtils so each copy animates its own bones. The free characters are pinned files at fixed commits or releases, each checked against its size and SHA-256 before anything is written, with licences recorded (one needs CC BY credit). 2D sprites are sheets of equal frames listed per state; Godot builds an AnimatedSprite2D from AtlasTexture regions.
14. **Imported sounds replace built-in ones by name; textures are projected, not unwrapped.** Rules name a template's generated sounds (chime, gate, coin, jump ...), and a level's `audio` maps any of them to an imported file and adds looping music, so rule graphs, the IR and the Unity and Unreal hosts stay unchanged (those engines keep their generated sounds). Both templates' `sound_bank.gd` play through a small pool of players so sounds can overlap, and stop everything before the game quits so no playback leaks. Built-in objects are made of primitive meshes whose UV layouts do not tile well, so an object's texture set is projected from the three axes in world space and repeated every `tile` metres (Godot's `uv1_triplanar` with `uv1_world_triplanar`); the studio's 3D view patches three.js's shader with the same weights and flips. Platform pictures repeat every `tile` tiles from the platform's top left, in the game (a Polygon2D) and in the side view (an SVG pattern).
